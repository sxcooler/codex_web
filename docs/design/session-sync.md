# 会话同步与性能

日期：2026-09-11。已合并增量同步、传输优化与列表性能设计及实施记录；以下使用最终窗口分页规则。

2026-09-20 补充：释放只读取状态头；较早历史及按需条目在旧协议下先定位再读正文；HTTP 断连停止后续历史分页；隐藏会话筛选单次最多 5 页。完整规则、测量与验证见 [功能链路性能审计](../verification/2026-09-20-performance-audit.md)。

## 目标与范围

首次进入或无法续传时加载会话快照，运行中通过 SSE 接收消息和状态增量。已完成历史不随每次文本输出重读或重传。保留外部客户端状态校正、手动刷新、审批、插话、附件、释放和重连能力。不新增依赖，不改变原生任务的执行语义。

## 同步契约

- 快照继续使用 GET /api/sessions/:id，增加同步水位 syncCursor。水位必须与快照的基线一致。
- SSE change 使用既有 id/threadId/kind，增加 revision 和 patch。patch 可包含 state（phase、activeTurnId、pending、error、permissions、retry、release、model）、thread（不含 turns 的头字段）、turn（按 id 合并）、item（{turnId,item} 替换）、delta（{turnId,itemId,field,offset,text}，field 仅 text 或 aggregatedOutput）。未变化的旧轮次和旧输出不进入文本增量事件。
- 每个会话 revision 连续，客户端丢弃重复/旧事件。轮次和消息按 id 合并；终态优先，文本增量使用 UTF-16 偏移量校验，已含有的文本不追加第二次，缺口触发重新同步。
- 首次快照与 SSE 建连之间用 syncCursor 续传；快照加载期间先断开旧流，完成后以该水位重连。原生 EventSource 重连使用 Last-Event-ID；主动建连可通过受校验的 cursor 查询参数续传。
- 回放缓冲按字节限制；过期游标、运行时重启、不能表达的变化或超大事件发送 resync。心跳和 ready 不再触发完整历史请求。
- 手动刷新执行权威快照；正常发送/审批响应不重建 SSE。定期轻量状态校验覆盖其他客户端工作及漏失终态，必要时才重新读取变化轮次。缓存不可使发送权限校验依赖过时状态。

## 缓存与边界

复用 Runtime 的 liveTurns；已完成正文复用浏览器已有历史。服务端保存有界头字段、完整轻量轮次签名与 64KiB SSE 回放缓冲；不是完整正文缓存。浏览器首次取最近 3 轮，内部写入/恢复/权限判断仍读权威历史。状态检查不读取消息 items 分页，禁止用 UI 缓存绕过运行状态检查。窗口与按需输出规则见下文。早期提出的全局 8MiB 缓存预算及“不增加分页 UI”已被最终实现替代，不作为当前配置。

## 验收

长对话接收连续文本增量时，全量会话 GET 数量不随增量次数增长，增量不包含旧命令输出；终态历史不反复请求原生 items 分页。覆盖重复事件、断线回放、游标过期、运行时换代、快照/增量交错、最终消息替换、审批结束、原文复制、乐观消息去重与附件。运行全量测试、构建及真实浏览器模拟 API 验证，随后打包并校验解压运行与归档内容。

## 实施结果与实际边界

- 新增 `GET /api/sessions/:id/status?epoch=…`，返回 `{resync:boolean}`。每 30 秒及页面重新可见时校验原生头/轮次状态，正常输出不读取历史正文。空会话沿用同 epoch 的未持久化兼容分支。
- 快照在原生分页读取期间记录变化，合并终态和缺失消息后给出一致的 revision/syncCursor；原生已有的终态消息保留权威替换。活动原生正文用于初始化后续 delta 偏移。
- SSE 回放沿用 64KiB 总字节上限；单个补丁超过上限转换成 resync。内部快照补齐仍保留大终态内容。游标过期、换代、缺口及超大事件才重载基线。
- 插话受理后仅分页当前轮次，根据 clientId 找到原生用户消息并发布补丁；无法确认时回退重新同步，不伪造原生消息 ID。带附件发送后一次权威刷新补齐附件预览。
- 消息组件使用 React.memo，未变化的历史对象保持引用，避免每次增量重复渲染旧命令输出。
- 同步前后不更改运行中任务权限或发送验证。新后端协议需要服务重启后生效，本轮未中断现有服务。

## 会话传输与历史加载优化

以下是后续已实施的 gzip、耗时统计、最近历史分页、命令输出按需加载及列表优化。

### 设计

1. **gzip**：通过 Node zlib 异步压缩大于等于 1KiB 的 JSON、HTML、JS、CSS、SVG 文本响应。按 Accept-Encoding 协商，遵守 gzip;q=0、Vary、现有 Content-Encoding、HEAD/204/304 和 no-transform；压缩无收益时保留原文。SSE 和图片等二进制跳过，不改变流式输出时机；静态资源已有缓存策略保留。认证响应跳过压缩，不启用请求解压。
2. **耗时统计**：用 Server-Timing 展示服务端处理时间和 gzip 时间；X-Response-Uncompressed-Bytes 与 X-Response-Bytes 表示本次响应体压缩前后字节数。可直接在开发者工具中比较首次历史、后续分页、输出加载与状态请求。不记录会话正文、路径或用户标识，不新增监控服务。指标不代表浏览器渲染耗时或网络往返耗时。
3. **最近历史分页**：浏览器首次快照只加载最近 3 轮，按时间正序显示；顶部提供“加载更早消息”，每次 20 轮，加载后保持阅读位置。GET /api/sessions/:id 使用窗口快照；响应 history: {nextCursor:string|null}，游标为本页最早轮次 ID。GET /api/sessions/:id/history?before=游标 返回 {turns, nextCursor}；失效游标返回可重试错误而不静默跳过历史。为兼容外部客户端校正，可读取全部轻量轮次头，只读取当前窗口的消息正文。内部发送/恢复/权限判断仍保留权威读取，不以 UI 窗口替代安全判断。
4. **命令输出按需加载**：已完成命令输出超过 8KiB 时，快照、分页和终态 SSE 仅附前 2048 个字符，并标记 outputDeferred、outputChars、outputBytes。展开命令后 GET /api/sessions/:id/turns/:turnId/items/:itemId/output 返回 {output:string}，该组件会话内缓存结果，错误可重试。运行中命令保留现有增量及偏移语义，不截断正在流式输出的内容。权限校验与现有 API 一致，接口仅返回指定会话、轮次、命令的输出。

### 同步边界

窗口快照继续返回 epoch/revision/syncCursor，并合并加载期间的事件。轻量状态比较保留完整轮次头签名，不能因未加载的旧正文而持续 resync。加载更早历史只合并不存在的轮次，不覆盖更新的实时消息、状态或水位。手动刷新/断线补齐重建最近窗口；已展开的历史需重新加载，避免保留不确定的陈旧正文。切换会话时取消旧分页和输出请求。

### 验收

- 压缩往返内容一致，协商禁用、短响应、SSE、缓存和认证边界正确；指标字节数可核对。
- 超过 3 轮的历史首次不读取旧轮次正文；逐页无重复和遗漏，失效游标明确失败。
- 大型已完成命令输出不进入初始响应/终态 SSE；按需取回原文，运行中增量不丢失。
- 浏览器验证加载历史保持视口，展开输出首次请求、折叠重开复用，失败可重试；既有发送/插话及增量同步回归通过。
- 运行项目测试、生产构建和独立复核，不重启当前正在承载任务的服务。

### 已知范围

单个运行中命令和单条超大文本消息仍可能较大；本轮不增加虚拟列表、ETag、Brotli、全文缓存或外部监控。原生协议没有正文投影，本轮减少浏览器传输和未选中轮次读取；读取选中轮次时仍会从原生进程收到该轮命令原文。

### 最近会话列表重复请求与慢扫描修复

## 首屏原生历史读取延迟修复（2026-09-20）

- 首次打开、手动刷新和断线重建统一只读取最近 **3 轮正文**；“加载更早消息”仍每页 20 轮。使用同一窗口函数选择原生正文与生成浏览器响应，不能只截短返回值却仍提前读取 20 轮。
- 完整轻量轮次头、epoch/revision/SSE 水位、加载期间的实时事件合并和原生权限校验保留；窗口外的运行状态仍参与判断。内部完整读取及图片/命令原文按需读取不受首屏窗口影响。
- 旧会话不支持 item 分页时，每轮正文通过一次 full RPC 读取。首屏最多 3 轮，而不是最多 20 轮；不通过合并多轮 full 响应突破 16 MiB 协议帧限制，也不增加全文缓存、轮次并发或静默后台预取。
- 首屏轮数是调用数量上限，不是时间或字节保证：单个大轮次仍可能慢；显式加载较早的 20 轮也可能较慢。需要更细分页时应使用原生 item 分页能力，而非绕过原生存储读取或放宽超时。
- 回归覆盖两种原生协议、完整分页无遗漏、输出按需读取、窗口外的活动状态、加载中事件、刷新丢弃旧分页、桌面与手机阅读锚点。测量与本次验证见 [性能审计补充](../verification/2026-09-20-performance-audit.md#首屏仍串行读取过多原生正文)。

### 超时与网络错误提示

- `AbortSignal.timeout` 到期时，读取接口显示“读取超时”，不再一律显示“无法连接服务器”；覆盖等待响应头及读取响应正文两阶段。真正的 fetch 连接错误继续提示检查网络，导航取消保留取消语义，HTTP 错误保留状态码和服务端错误内容。
- 写入请求超时仍明确“提交结果待核实”，不会标记为确定失败或自动重发；现有消息幂等和历史核对流程保留。
- 前端重新构建/刷新不会重载正在运行的 Node 后端。排查是否应用性能修复时，应核对服务启动时间与后端提交时间；Windows 从 SSH 操作时仍需在已登录的桌面用户会话中启动。
- 回归先复现超时误报断网，再覆盖响应头/正文超时、写入未知结果、取消、网络及 HTTP 错误；API、同步和提交专项共 11 项通过，TypeScript 和生产构建通过。

### 新会话原生历史写入竞态

- 2026-09-21 使用 Codex CLI 0.153.4 实测：`thread/start` 和首条 `turn/start` 已成功返回，紧接着 `thread/read` 仍可能报 `failed to read thread: thread-store internal error: failed to read session metadata …: rollout at … is empty`；约 300 毫秒后的读取恢复正常。这是原生元数据尚未写入的窗口，不能等同于整个 runtime 不可用。
- 在共享 RPC 调用层仅对此明确的 `thread/read` 错误按 50、100、200、400 毫秒间隔重试，最多五次读取；快照、状态检查、工作目录读取等入口共用。正常读取不增加等待，其他错误不重试。
- 超出重试上限返回 `RUNTIME_HISTORY_NOT_READY`，提示原生记录仍为空；不无限等待、不把损坏记录伪装成空会话、不回传原生私有路径。写入操作绝不因此自动重发，提交结果未知的语义保持不变。
- 回归覆盖首条消息已接受时的快照恢复、运行中轮次保留、读取次数上限、无关读取错误及写入不重放。
- 验证：真实新会话在两次原生空记录错误后首次快照正常返回 RUNNING，等待间隔合计 150 毫秒，未重发首条消息；两个回归测试先失败再通过。正常用户权限下全量测试 232 项通过、5 项条件跳过，TypeScript 和生产构建通过。沙箱内首次全量运行的 Git fetch helper 清理测试挂起，停止对应测试并清理已确认的测试 helper 后，在正常权限下重跑通过；未重启当前 Web 服务。

## 历史附录：实施与交付
