## 已确定的日志和恢复缺口

`scripts/windows/background-host.ps1` 将 Node 的 stdout/stderr 转写到轮转的 `server.log`，管道结束后直接 `exit $LASTEXITCODE`。它没有持久记录宿主启动身份、管道结束、子进程最终退出码或宿主失败。

`src/server/diagnostics.ts` 是可选的异步队列。正常关闭会写 `stop` 并等待落盘，但当前保留记录没有 `stop`。进程致命退出、宿主被终止时，不能依靠尚未刷新的异步队列还原最后事件。

API 异常目前在普通模式也会保存 message/stack；这条路径只覆盖 Fastify 请求处理，不能覆盖 Web 进程级退出。工作进程的启动入口还存在只打印 message 的异常路径。

原生 Codex 子进程已有 `native_exit`（退出码、信号、是否预期）和 `native_failure` 事件，`Runtime.onFailure` 会更新会话错误并保留 Web。当前保留日志没有这些事件；这是本次缺少对应证据，并非源码完全没有捕获原生退出。

当前启动机制是用户登录时启动一次；宿主跟随 Node 结束，没有中途恢复机制。这足以解释退出后一直 502，但不能解释最初为何退出。

源码中已检查的原生关闭、标题清理和 Git 超时清理都指向自己创建的子进程，没有找到“任务完成后关闭 Web 或后台宿主”的直接路径。外部强制终止、Windows Job 生命周期、宿主故障或未捕获异常仍待新的退出证据区分。

## 已确认的最小修补范围

目的：让下一次退出能分辨启动失败、受控停止、JS 致命错误、Node 退出与宿主管道结束。此改动补可观测性，不宣称修复尚未确定的首因。

1. **后台宿主记录**：在原有轮转日志中记录 host_start、host_end/host_error，包含宿主 PID、可取得的父进程身份和实际 Node 退出码。管道结束后立即保存退出码，避免后续记录动作覆盖它。保留现有退出行为。
2. **工作进程记录**：普通模式也记录启动、就绪、认证控制停止请求、信号、关停开始/成功/失败及最终退出码；受控停止带明确原因。只记录阶段、PID、端口、错误 name/code/message/stack 等白名单字段，不展开配置、请求头、请求体或错误自定义属性。保留错误 message/stack，同时对已知 token、Bearer、cookie 和凭据模式脱敏并限长，以 secret sentinel 验证。字段白名单不等于内容脱敏，不能保证任意错误自由文本均无敏感内容；这些记录仅留在本机，不作为接口响应或未经检查的分享材料。
3. **致命事件**：在入口尽早安装 `uncaughtExceptionMonitor`，用同步、脱敏、限长、轮转、尽力写入的本地结构化记录保存异常来源、message/stack。由它观察默认致命退出的未处理拒绝，不额外注册改变行为的 `unhandledRejection` 处理器。保留 Node 默认致命退出及其 stderr 输出行为，不增加吞掉异常或继续运行的处理器。记录失败不能改变原错误或退出码。
4. **一致性检查**：读取 `main.ts` 和 `server-control.ts` 的两个信号关闭入口，消除重复调用和错误遗漏时需保持原有幂等关闭、控制身份校验及资源释放语义。仅在测试证明必要时修改，不顺带重构运行时。
5. **隔离验证**：先新增会失败的测试，再实施最小改动。覆盖普通/诊断模式，正常退出、关闭抛错、启动抛错、未捕获异常/未处理拒绝，Windows 宿主保留真实退出码，以及日志失败不改变退出结果。使用临时目录、随机端口和测试子进程，不访问真实会话和 3000 端口。运行相关回归、项目完整测试与 TypeScript 检查。

同步记录也不能在整个进程树被强制结束时保证写到最终事件。持续自动恢复、Windows 服务化或改变 Job 隔离属于另一项运行方式决策，需要先取得对应证据与授权；本次方案不引入周期性自动重启。
