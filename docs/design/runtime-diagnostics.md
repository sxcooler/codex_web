# 无响应诊断

2026-09-22 用户确认：先加入最小诊断，再复现多个会话同时读取超时。目标是区分 Web 事件循环阻塞、原生 RPC 等待和共享项目访问的相关性，不自动重启、不重发请求、不修改锁策略。

- 默认关闭，启动时显式添加 `--diagnostics` 才启用本次运行的诊断；不保存到配置或登录自启，下次普通启动恢复关闭，也不会清除已有日志。关闭时不注册诊断采样器或 HTTP 诊断钩子。
- 启用后所有启动入口共用 `.local/web/diagnostics.jsonl`；每条包含时间、Web PID，原生进程启动/退出记录 native PID。单文件上限 1 MiB，保留一个轮转文件，写入队列也限制大小；写日志失败不能影响业务。
- 每 10 秒采样 Web CPU 增量、RSS/堆大小、事件循环延迟、HTTP/RPC 在途数与有限的等待明细。采样只读取内存，不调用原生 RPC，不唤醒空闲运行时。循环被完全卡住时采样也会停止，日志缺口是线索，不能单凭缺口断言死锁。
- HTTP 超过 1 秒、服务端错误或响应中断记录路由模板和耗时。正常 SSE 长连接单独计数，不作为慢请求；请求方法、服务端生成的请求编号可关联等待记录。
- RPC 超过 1 秒、超时、协议/进程故障记录方法、编号、耗时、原生 PID 及安全错误分类。保留超时后“不自动重试”的现有语义。
- 只记录校验后的会话 ID、项目路径摘要和计数，不记录正文、工具参数/输出、图片、文件路径、URL 查询、Cookie、Token 或原始 stderr/错误文本。
- 测试覆盖超时不重发、两个会话的等待信息、敏感信息不落盘、HTTP 等待/结束/中断、采样与日志轮转。验证后提交；运行服务重启时间另与用户协调，不能终止承载当前工作的进程。

诊断规则：CPU 增量和事件循环延迟同时升高，优先调查 Web 同步处理；Web 正常而多个 RPC 长时间等待，优先调查共享 app-server；相同项目摘要的请求同时变慢再结合具体方法判断项目资源竞争。每种现象都需证据，不能从单张累计 CPU 截图下结论。

## 复现与保留证据

更新代码后，等当前任务停稳，再使用下面对应入口带参数启动；不会自动停止现有服务。若实例正在运行但未开启诊断，后台/便携启动入口会提示先停止再重启，不会假装已开启。已经开启诊断的实例会保持原状态，直到停止。

| 入口 | 本次启用诊断 |
| --- | --- |
| 源码前台 | `npm start -- --diagnostics` |
| Windows 源码后台 | `scripts\windows\start-server.cmd --diagnostics` |
| Linux 源码 | `bash scripts/linux/start-server.sh --diagnostics`（后台再加 `--background`） |
| Windows 便携包 | `Start.cmd --diagnostics` |
| Linux 便携包 | `bash Start.sh --diagnostics` |

PowerShell 直接调用 `start-server.ps1` 同样支持 `--diagnostics`，后台再加 `-Background`。启动输出会提示诊断已启用，托管实例状态入口显示 `diagnostics: on/off`。出现本次 PID 对应的 `start` 记录且每约 10 秒出现 `sample`，才能确认这份诊断已启用；历史日志存在不代表当前已启用。

再次遇到读取超时，记下时间，尽量先保留 `diagnostics.jsonl` 和 `diagnostics.jsonl.1`，再决定是否重启。这些文件位于忽略的本地数据目录，不上传 GitHub。`start.pid` 是 Web Node 进程；`native_start.nativePid` 是它启动的 Codex 子进程。CPU 字段表示本次采样间隔内累计消耗的毫秒，不是百分比；与 `intervalMs` 对照判断负载。

日志不自动抓取调用栈，也不采集原生子进程的 CPU；严重卡死期间可能无法写入最后一批异步日志。若 `sample` 完全停止，只能确认采样不再推进，仍需结合现场 PID/CPU 或后续人工调用栈诊断。原生 stderr 继续只计数，RPC 错误只记录错误码和安全分类，不保存可能含对话的原文。

项目摘要使用已经返回的原生 metadata，不新增查询，不取得会话写入所有权。纯读取卡在历史分页时也能关联；若第一次 `thread/read` 本身尚未返回，则该会话没有项目摘要，不能凭空归属。等待中的会话优先纳入有限的采样明细。
