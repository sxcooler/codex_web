# Git 变更文件列表耗时调查

日期：2026-10-09。范围：调查用户报告的 2200 多个临时文件、`files?staged=false` 耗时 8.21 秒；本次没有实施产品优化、清理真实文件或重启服务。

## 结论

8.21 秒属于明显偏慢的列表体验。当前测量证明逐文件处理阶段自身可以耗掉约 8 秒，但原现场请求没有阶段记录，精确归因尚未完成。不能把它直接归为 Git 扫描慢、网络代理慢或浏览器渲染慢。

该接口为了在每行显示新增行数和二进制标记，会逐个串行读取未跟踪文件。初次隔离样本中的文件读取占了原接口总耗时约 97%，而 Git 状态扫描仅占约 61 毫秒。保留相同安全检查的 4 路并发诊断原型，将这一读取阶段从 4.25 秒降到 2.40 秒；这是单次样本结果，不是原现场请求的提速承诺。后续相同文件集合出现较大耗时波动，因此这一单次比例不能作为稳定收益依据。

用户指出 `0.061 + 4.25` 无法解释现场 `8.195` 秒。这一质疑成立：前两项属于隔离样本，不能当成现场请求的分段，也不能把两套样本相减后的约 3.9 秒当作已经发现的另一个瓶颈。

## 源码中的成本

链路：`boundProject → runtime.threadCwd → projectForCwd → Projects.list → gitFiles → gitStatus → 每个未跟踪文件的 readFile → revision`。

关键位置：

- `src/server/api.ts:229`、`:240`：绑定项目后调用 `gitFiles`；项目列表在绑定阶段扫描一次 WORK_ROOT。
- `src/projects.ts:316`：`gitStatus` 执行一次 `status --porcelain=v1 -z --untracked-files=all`。
- `src/projects.ts:437`：已跟踪文件的 numstat 已一次批量处理；未跟踪文件在循环中串行 `await readFile`。
- `src/projects.ts:336`、`:419`：读取保留项目、路径、敏感文件和目录链接校验，随后解码文本并分行；`gitFiles` 又分行一次来统计新增行数。
- `src/projects.ts:432`：每次 bounded read 固定分配 `maxBytes + 1` 缓冲；普通文件查看上限为 1 MiB。
- `src/web/GitPanel.tsx:76`：列表即时显示二进制标记或 `+N −N`，因此延后统计会改变界面行为。

默认情况下，每个未跟踪文件约有 3 次 realpath、4 次 lstat，以及 open/read/close。当前配置 `allowProjectDirectoryLinks=true`，还会逐级检查文件祖先路径的 realpath；目录越深，检查次数越多。已知项目的 `resolve` 不会每个文件重新扫描 WORK_ROOT，也不做子仓库发现，不应归因为 N 次仓库扫描。

2200 个文件的普通读取缓冲累计申请约 2.15 GiB，即使文件很小。这是累计申请量，既不是峰值驻留内存，也不是实际磁盘读取量；本次没有单独证明缓冲申请是最大成本。

## 隔离测量

诊断脚本导入当前产品的 `Projects`，仅在独立进程包装公开方法计时，保留原 `resolve/readFile` 与全部安全检查，没有调用真实 HTTP/native RPC。

稳定样本位于 `.local/git-files-profile-20261009/fixtures/work/perf-files`：2200 个未跟踪文本文件，每个 256 字节、16 行，共 563200 字节（550 KiB）。使用与服务相同的目录链接设置。样本没有已跟踪修改，隔离仓库没有提交，revision 为 null；独立 `rev-parse HEAD` 返回 128 的记录保留在原始 JSON 中。

| 测量 | 耗时 | 口径 |
|---|---:|---|
| 现有 `gitFiles` 全流程 | 4386.8 ms | 包含 status、读取、组装、revision |
| 上述 status | 61.3 ms | 包含项目解析与状态解析 |
| 上述串行文件读取累计 | 4245.4 ms | 2200 次读取，含轻量计时包装 |
| 相同路径，4 路并发读取 | 2401.6 ms | 仅文件读取阶段的墙钟耗时 |
| 相同路径，8 路并发读取 | 2510.5 ms | 仅文件读取阶段的墙钟耗时 |

同口径读取阶段的 4 路原型耗时减少约 43%。8 路没有进一步收益，不建议盲目增加并发。并发情况下各文件耗时之和包含重叠，不能当作总耗时。

三轮均读取 2200 个文件，失败、二进制、截断均为 0；size、新增行数、binary、truncated 和路径字段一致的断言通过，按原 Git 状态顺序组装结果的断言也通过。真实 Git 返回顺序可保留，读取完成顺序可以不同。

边界：每种策略只测一轮；文件创建及重复读取使缓存已预热；原始文件体积和目录深度未知；该实验没有包含浏览器、网络、原生会话读取及现场并发负载。不能把该比例直接套用到 8.21 秒。

## 建议方案，尚未实施

### 进一步测量：同一轮分段可加总，但不等于历史复原

再次使用固定的 2200 个、每个 256 字节/16 行文件。先以独立进程包装原 fs.promises、FileHandle 和 Git 执行方法计数，再运行关闭底层包装的对照。所有安全检查保留；没有调用真实 API/RPC、改变服务或追读不断变化的真实文件。

关闭底层包装、仅保留原公开方法轻量计时的一轮：

| 阶段 | 耗时 |
|---|---:|
| Git 状态与项目解析 | 33.9 ms |
| 2200 个文件的逐文件处理 | 8572.4 ms |
| 其余，含 revision、组装及计时残余 | 147.9 ms |
| 同一轮总计 | 8754.3 ms |

这次数字属于同一轮，可以加总。能确认 8 秒级总耗时可以集中在逐文件处理阶段，不需要假设另一个固定的 4 秒阶段。

但相同平级样本、同一无底层包装进程的前后结果分别为：总计 2068.6/8754.3 ms，逐文件处理 1983.5/8572.4 ms。文件数量、大小、内容未变，结果及顺序断言通过。这种变化说明缓存、机器负载、存储和调度等条件尚未分离；不能把之前的某个单次值当作恒定成本。

六级嵌套样本增加了 13200 次祖先 realpath 检查；无底层包装时总耗时 9819.0 ms、逐文件处理 9666.8 ms。由于平级前后本身波动很大，不能把所有平级/深层差值归因目录深度。

带底层包装的首轮平级样本总计 7845.2 ms、逐文件处理 7720.0 ms；其文件处理中的观测成本约为 realpath 3408 ms、lstat 1686 ms、open 516 ms、read 1091 ms、close 366 ms，其余约 653 ms。它体现了反复文件系统检查的成本分布，但包含包装干扰和当前机器条件，不能视为原请求 216 的分解。一次执行器包装接错返回结构导致的诊断失败发生在文件读取前、读取数为 0，失败 JSON 保留，修正后才有这些测量。

其他低成本阶段单独复核：WORK_ROOT 当前返回 7 个项目，三次扫描为 9.67/4.36/2.34 ms；2200 行元数据序列化为 0.15～0.24 ms、Buffer 转换约 0.05 ms、gzip 为 0.61～2.03 ms，响应未压缩 184827 字节、压缩 6555 字节。这些当前测量未出现秒级耗时，不能加到历史 8.195 秒来推算当时占比。

### 请求 216 的历史窗口

估算窗口为北京时间 13:26:44.987～13:26:53.182。窗口周边日志 dropped/writeFailures 均为 0；慢 RPC 只有 account/rateLimits/read，没有达到 1 秒的 thread/read 记录。原生头信息只复用进行中的 Promise，完成后删除；成功且不足 1 秒的 RPC 有意不记录，因此不能声称该请求没有读取原生头信息。现有证据不支持数秒原生头 RPC 是主因。

13:26:52.375 的十秒采样记录 Web 进程 CPU user/system 为 3641/3000 ms、event-loop 最大延迟 32 ms，活动 HTTP 只有请求 216，native pending 为 account/rateLimits/read。CPU 属于整个 Web 进程，不可全部分配给该请求；32 ms 不支持该窗口出现数秒同步事件循环阻塞。native receivedBytes 属于协议字节，不是文件读取字节。

原样本缺失和阶段记录缺失仍然阻止精确复原。再次出现的真实未跟踪文件也快速变化：主会话只读状态计数曾见 1117 条、其中 1103 条未跟踪；单轮诊断开始时只剩 18 条、其中 3 条未跟踪，总耗时 159.6 ms。开始时已保存后一批路径，保留读取失败计数；这些变化后的样本不作为现场提速证据。

### 优先补齐同一次现场请求的证据，再决定性能修改

建议在诊断模式记录同一个请求 ID 下的原生 cwd 读取、WORK_ROOT 扫描、Git status、tracked numstat、未跟踪文件处理、revision 分段，以及文件数、实际/估计读取量、目录深度摘要和失败计数。现有 `Server-Timing app/gzip` 与响应字节头可以复用；应将其保存到同一请求记录，留下序列化/压缩阶段及总耗时的校验关系。避免记录文件内容、凭据和完整请求体，不增加每个文件一条日志或额外文件读取。

这一诊断方案尚未写入产品。下面的并发和读取优化保留为候选，不能提前把单次 43% 差值承诺为现场收益。

1. 首先只调整未跟踪文件的读取为固定小并发，优先验证 4 路；沿用现有安全读取，保持输出顺序、统计字段及错误语义。避免一次启动数千个读取。
2. 随后单独测量小文件缓冲、重复 lstat 和重复分行的成本，按实际文件大小限制分配，保留现有读取上限及文件变化处理；若修改共享读取方法，回归图片、报告、Git 元数据和 patch 的边界。
3. 复用已解析项目需谨慎。不能直接删除每次 `resolve` 或路径检查：应继续拒绝项目根被换成外部 junction、移出 WORK_ROOT、敏感路径及不允许的文件链接。
4. 若上述仍不足，再讨论列表先显示路径、按需统计行数。这涉及列表 `+N −N` 和二进制状态的加载展示，需要另外设计确认。

实施验证应覆盖文本/二进制、嵌套路径、重命名、暂存区、大文件/行数截断、敏感文件、junction/链接、文件消失和读取失败；稳定大样本用于比较耗时，不设置受机器负载影响的硬性毫秒测试阈值。现场复测需记录文件数量、体积、目录深度以及每阶段耗时，不能拿不同文件集合比较优化结果。
