# 已完成轮次误报中止的修复设计

日期：2026-11-01。状态：实现与隔离验收完成，尚未合并或部署；设计与计划先于代码提交。

## 用户要求与已知证据

用户原话：**“你先解决本轮已中止的问题吧，记得先落文档”。**

目标是让时间线、顶部状态和后续同步尊重同一轮次的原生结果。当前截图中耗时 539,168 ms 的轮次显示“本轮已中止”，原生持久化历史却是 `completed`，并有 `final_answer` 消息。线上入口与回滚构建的哈希一致；旧的终态一致性修复仍在，不能归因为回滚漏文件。

此前[终态一致性计划](../superpowers/plans/2026-10-30-turn-terminal-consistency.md)主要覆盖活动轮次与错误终态冲突。本次补充“已经锁存 interrupted，后续只读历史确认 completed”的方向。首次错误 interrupted 究竟来自原生通知、原生读取还是 Web 缓存，仍须核对，不能把待验证推断写成生产首因。

原始截图、会话 ID 和本机查询记录留在忽略的 `.local/turn-completion-20261101/`，不把用户正文、私有路径或完整 RPC 载荷加入仓库。

## 范围与约束

- 仅修复轮次终态判定与同步；压缩传输失败、提供商功能和泛化的 UNKNOWN 权限提示不在本次范围。
- 新鲜、同一运行时且没有并发更新活动的原生完整终态，可以纠正同 ID 的旧终态缓存；不同轮次不能互相覆盖。
- 真实 `interrupted`、`failed` 保留对应结果；不得凭“存在最终回答”推断 completed，也不简单隐藏中止横幅。
- 旧 started/item/delta 仍不能复活真实终态。历史读取期间收到更新事件时，旧读取不能回滚新证据。
- 核对复用现有只读 API、同步水位和有界核对机制；失败不能伪报完成、空闲或允许重复提交。
- 不修改用户 rollout/SQLite，不自动重发、resume、abort、抢占 writer 或重启服务；不新增依赖。

## 方案与取舍

采用现有 Runtime → snapshot/SSE → SessionView 链路，在证据实际被错误锁存或接受的位置修复，并用同一条事件序列通过 Runtime 和浏览器回归。先核对原生协议读到的状态，再用 RED 测试固定缺口，避免只改变横幅文案。

实施时已复现两条缺口：完成通知之后返回的旧中止历史页会被直接接受；已确认终态之后的迟到终态通知会直接覆盖浏览器结果。前者复用既有 10 秒、同 epoch/activityRevision、single-flight 只读核对，核对未解决时保留原证据；后者只发 resync，等待权威历史，不直接接受迟到通知。最初错误 interrupted 的生产来源仍未被证明。

独立审查补充两项边界：用户明确点击“重新同步”时允许重试此前失败的终态核对，普通轮询不重置预算；较新的完整快照已被接受后，若较旧并发读取的终态头部与之不同，返回现有可重试同步错误，由既有客户端重读一次，不能再覆盖终态。没有终态差异的普通重叠读取保持原行为。

不采用“有 final_answer 就算完成”：真实中止也可能留下文字；不采用直接读取或修补原生 SQLite：这会形成第二套状态真相，并绕过现有协议与时序边界。

## 验收

1. 复现旧 interrupted 与新鲜 completed 的冲突；修复前测试明确失败，修复后显示完整最终回答且没有错误中止横幅。
2. 真实 interrupted/failed、旧终态与新活动、读取竞争、断线和重连继续保持正确，核对无原生写入副作用。
