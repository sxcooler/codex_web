### 已观察到的协议行为

- initialize → initialized 成功；account/read 检测到 ChatGPT 登录；model/list 返回 6 个可见模型。
- thread/start 返回持久化 Thread；只读沙箱、on-request 和 user 审批覆盖得到返回值确认。
- 首条纯文本 turn 收到 started、文字 delta 与 completed。
- turn 完成后 thread/read(includeTurns=true) 可读到用户标记；thread/unsubscribe 返回 unsubscribed。
- 完全退出 app-server 后，由新进程读取同一 Thread，用户标记仍在；显式 sourceKinds 列表可发现它。
- 当前版本返回 historyMode=paginated，但这次 includeTurns 历史读取有效。不能套用旧文档中 paginated 一定不能完整读取的假设；后续长历史仍需验证分页能力。
- 当前版本返回 source=vscode。首次检查发现宿主存在 CODEX_INTERNAL_ORIGINATOR_OVERRIDE；客户端随后排除三个父客户端身份变量，重新 start 仍返回 vscode。这里只记录实测，不声称已定位服务端分类原因，也不把 source 字段当成 VS Code UI 操作证据。
- 首次成功 turn 期间还收到 error/warning 通知，最终终态为 completed；记录事件计数，不将中间通知直接等同于最终失败。尚未据此定位通知原因。
- 中断时序实测：turn/start 返回 inProgress 后立刻 interrupt，两次得到 no active turn to interrupt，且此前尚未收到 turn/started。改为等待匹配 Thread/Turn 的 started 通知后，interrupt 成功并收到 interrupted，历史读取和取消订阅也成功。此检查保留为 `probe -- interrupt`，不使用固定延迟掩盖竞态。

### VS Code UI 发现与占用问题

用户反馈历史列表找不到测试 Thread。进一步只读检查确认：

- 测试记录实际位于默认 `.codex/sessions/2026/09/09/`，cwd 为当前项目，未归档，section/projectId 均为 null。
- 原生默认列表、cwd 筛选、state DB 查询、vscode 来源筛选及 unsectioned 筛选全部命中；路径盘符小写和全路径小写同样命中。
- VS Code 工作区元数据确认为 `file:///c%3A/Users/example/work/codex_web`，没有打开另一个项目的证据。
- 仅为兼容诊断运行扩展内置 0.153.0 的读取请求，它也能读取完整历史并在默认项目列表找到同一 Thread；项目后端不依赖该内置 binary。
- 公开扩展 manifest 没有提供导入 Thread 或按 UUID 打开历史的命令；不拼造未公开的 deep link，也不修改原生数据库。

用户随后更新 VS Code，截图显示包含当前 REMOTE-PROBE-EXAMPLE 标记的会话及更早的测试会话。用户在当前测试会话发送了约定的 VSCODE-REPLY 标记并确认完成；独立 CLI 只读检查确认该标记存在于用户消息，两个 Turn 均为 completed。更新后 UI 可见，但尚不能证明之前的具体故障原因就是版本差异。

运行 verify 时，标记校验通过，随后 thread/resume 返回 `thread 00000000-0000-4000-8000-000000000008 already has an active writer`。此时尚未调用 turn/start，状态中无 returnAttemptedAt，没有发送或重发回程消息。实测说明 Turn 完成不等于外部客户端已释放写入占用；只读历史可用也不等于能够恢复写入。已请求用户保存工作并关闭相应 VS Code 窗口，再验证释放后的接手行为。不得强制结束其他客户端或修改原生锁文件。

同时修正 read 的显示：externalUserMarkerFound 直接检查本次读取的原生用户消息，不再依赖 verify 成功后保存的旧状态。真实 `probe -- read` 返回 turns=2、listed=true、externalUserMarkerFound=true；修改后 `npm test` 仍为 24/24 通过。

人工步骤修正：实施助手本身运行于同一 VS Code 窗口，不能要求用户关闭后立即在该窗口回复。改为先打开独立 PowerShell，保存工作并关闭 VS Code，在独立终端运行现有 verify，等待结束后再重开 VS Code 回报。

此步骤已实测成功：用户提供回程 Turn `00000000-0000-4000-8000-000000000009` 的 started/completed 输出。`.local/probe.json` 保存了 returnTurnId、externalUserMarkerFound=true 和 release.status=unsubscribed；独立新进程再次运行 read 返回原 Thread ID、turns=3、listed=true、externalUserMarkerFound=true。verify 输出中的 turns=2 来自发回程前的快照，不代表回程丢失。

结论限于同一 Thread 的协议端 → VS Code 真实 UI → 协议端往返，且 VS Code 退出后接手。单独由 VS Code 新建、其他客户端，以及保留 VS Code 进程时的即时释放仍须分别验证；关闭窗口是本次可重复步骤，不将其包装成无缝接力。

本机扩展 manifest 的公开命令中未发现单独释放 Thread 的入口。[官方 app-server 文档](https://learn.chatgpt.com/docs/app-server#unsubscribe-from-a-loaded-thread)说明 unsubscribe 只取消当前连接的订阅，最后一个订阅者退出后仍有无活动宽限期；因此未将“切换聊天/关闭测试页”视为立即释放写入占用的已验证办法。

### 修复与边界

1. Fastify 会把编码路径映射到真实路由，原始 URL 前缀不足以作为鉴权依据。实测 `/%61pi/settings` 曾在未登录时返回 200；现使用匹配路由的元数据统一鉴权、公开路由判定和 no-store，并以回归测试确认 401。
2. Fastify 默认 AJV 会把数值或单元素数组转为字符串。现关闭类型转换和多余字段删除：非法密码类型返回 400，且不消耗五次密码校验额度；额外字段也被拒绝。

其余自动检查覆盖 Host/Origin/CSRF、重复 Cookie、HTTPS Secure、固定脱敏错误、过期 token、数据库只存散列、密码修改后的全部旧会话失效、跨重启新密码、登录/改密竞态、32 会话上限及两个并行散列上限。

限速和改密协调采用单进程状态，适用于当前单实例设计。未来部署必须保持单实例；多进程协调、SSE 登录撤销通知以及更细的持久化故障注入属于后续集成范围。
