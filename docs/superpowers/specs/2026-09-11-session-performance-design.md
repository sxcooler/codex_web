# 会话传输与历史加载优化

用户确认先落文档再实施。本轮四项：gzip、耗时统计、最近历史分页、命令输出按需加载。

## 设计

1. **gzip**：通过 Node zlib 异步压缩大于等于 1KiB 的 JSON、HTML、JS、CSS、SVG 文本响应。按 Accept-Encoding 协商，遵守 gzip;q=0、Vary、现有 Content-Encoding、HEAD/204/304 和 no-transform；压缩无收益时保留原文。SSE 和图片等二进制跳过，不改变流式输出时机；静态资源已有缓存策略保留。认证响应跳过压缩，不启用请求解压。
2. **耗时统计**：用 Server-Timing 展示服务端处理时间和 gzip 时间；X-Response-Uncompressed-Bytes 与 X-Response-Bytes 表示本次响应体压缩前后字节数。可直接在开发者工具中比较首次历史、后续分页、输出加载与状态请求。不记录会话正文、路径或用户标识，不新增监控服务。指标不代表浏览器渲染耗时或网络往返耗时。
3. **最近历史分页**：浏览器首次快照只加载最近 20 轮，按时间正序显示；顶部提供“加载更早消息”，每次 20 轮，加载后保持阅读位置。GET /api/sessions/:id 使用窗口快照；响应 history: {nextCursor:string|null}，游标为本页最早轮次 ID。GET /api/sessions/:id/history?before=游标 返回 {turns, nextCursor}；失效游标返回可重试错误而不静默跳过历史。为兼容外部客户端校正，可读取全部轻量轮次头，只读取当前窗口的消息正文。内部发送/恢复/权限判断仍保留权威读取，不以 UI 窗口替代安全判断。
4. **命令输出按需加载**：已完成命令输出超过 8KiB 时，快照、分页和终态 SSE 仅附前 2048 个字符，并标记 outputDeferred、outputChars、outputBytes。展开命令后 GET /api/sessions/:id/turns/:turnId/items/:itemId/output 返回 {output:string}，该组件会话内缓存结果，错误可重试。运行中命令保留现有增量及偏移语义，不截断正在流式输出的内容。权限校验与现有 API 一致，接口仅返回指定会话、轮次、命令的输出。

## 同步边界

窗口快照继续返回 epoch/revision/syncCursor，并合并加载期间的事件。轻量状态比较保留完整轮次头签名，不能因未加载的旧正文而持续 resync。加载更早历史只合并不存在的轮次，不覆盖更新的实时消息、状态或水位。手动刷新/断线补齐重建最近窗口；已展开的历史需重新加载，避免保留不确定的陈旧正文。切换会话时取消旧分页和输出请求。

## 验收

- 压缩往返内容一致，协商禁用、短响应、SSE、缓存和认证边界正确；指标字节数可核对。
- 超过 20 轮的历史首次不读取旧轮次正文；逐页无重复和遗漏，失效游标明确失败。
- 大型已完成命令输出不进入初始响应/终态 SSE；按需取回原文，运行中增量不丢失。
- 浏览器验证加载历史保持视口，展开输出首次请求、折叠重开复用，失败可重试；既有发送/插话及增量同步回归通过。
- 运行项目测试、生产构建和独立复核，不重启当前正在承载任务的服务。

## 已知范围

单个运行中命令和单条超大非命令消息仍可能较大；本轮不增加虚拟列表、ETag、Brotli、全文缓存或外部监控。原生协议没有正文投影，本轮减少浏览器传输和未选中轮次读取；读取选中轮次时仍会从原生进程收到该轮命令原文。

## 实施与验证记录

- 实现采用 Node zlib，无新增依赖；开发者工具 Network 的响应头可查看 Server-Timing、X-Response-Uncompressed-Bytes、X-Response-Bytes，Timing 中可查看服务端阶段耗时。
- 浏览器历史 GET 使用 snapshot(id, {window:true})，内部业务调用保留完整快照；history 页额外携带附件预览元数据，合并后旧图片仍可查看。
- 自动测试 159 项：158 通过、0 失败、1 项依赖便携包路径的产物检查默认跳过；TypeScript 与生产构建通过。
- Chrome 1400px / 390px 的生产资源验证：45 轮分 20/20/5 加载无重复遗漏，加载前后阅读锚点误差小于 5px，分页途中 SSE 文字保留；大命令首次展开取回全文，重开复用，读取失败可重试；刷新取消的旧分页不会污染新窗口。
- 既有 4.8MB 历史 / 100 次增量仅首次 GET、重复事件、轻量聚焦、快照续传、缺口恢复、终态、即时发送、插话、草稿与导航回归通过。测试使用模拟数据，不代表线上会话压缩率。
- 未中断或重启现有服务；后端接口和 gzip 在更新服务进程后生效。

独立复核覆盖分页与同步水位、按需输出范围、压缩边界及前端并发，修复了 HEAD 无响应体却统计有效载荷字节的问题；对应专项测试与类型检查通过。

## 最近会话列表重复请求与慢扫描修复

用户截图中的两次 sessions 是左侧列表，当前会话正文为 UUID 路由。重复原因：App 登录完成已加载列表，Session 第一次接受 IDLE/RELEASED 又被当成状态变化调用 onChanged。修复为首次仅建立状态基线，后续真正进入终态仍刷新列表；聚焦、pageshow、online、可见性与释放轮询在同查询已请求中时合并，用户操作和任务状态变化仍可发起新读取，避免使用操作前的旧列表。

慢请求来自原生 thread/list 默认扫描 JSONL rollout 修补元数据；不是这十几 KiB 响应的下载时间。本地生成协议 ThreadListParams 提供 useStateDbOnly，现使用 true 直接查询原生状态数据库，不新增缓存、不直接访问内部数据库文件、不改变正文读取或任务权限。

本机只读测量：原默认请求 4190ms，限制20条仍为5408/5819ms；数据库直读91/97ms。扫描与直读返回相同22个会话及顺序，部分原生路径、cwd表示和活动更新时间存在差异，列表不使用这些字段作为执行工作目录。修复后的 Runtime.list 三次为183/98/98ms，第一次包含原生进程初始化。以上是本地进程调用耗时，不是线上网络端到端保证；截图中6.74/10.64秒的逐段耗时未直接采集。

回归先复现“首次加载重复请求会话列表”失败，再验证桌面/手机首次列表仅一次、并发唤醒合并。全量160项：159通过、1项便携包产物测试默认跳过，构建及既有分页、同步、发送浏览器用例通过。后端需要重启后生效，本次未中断当前服务。
