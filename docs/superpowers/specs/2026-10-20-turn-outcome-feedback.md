# 会话轮次结果与执行过程反馈

日期：2026-10-20。状态：**已实施并完成本地前端交付，详见[验收记录](../../verification/2026-10-20-turn-outcome-feedback.md)。**

## 官方 App 对照后的确认调整

用户确认以下调整，本节优先于下文初稿示意：

- 保留每个失败轮次末尾一次主要结果，默认简短显示结果与原因，正文解释收进详情，恢复建议只在最新失败显示。
- 普通历史过程不显示“已记录”，只突出异常或未结束记录。
- 补充原生压缩进行中及重连状态。明确压缩记录运行超过 10 秒才追加“可能需要几分钟”，原生 retry 只展示、不触发新的执行。
- 沿用现有暗色主题，不新增浅色切换。浏览器验收覆盖桌面／窄屏和中英文。
- 本次不增加服务繁忙自动重试，不承诺消除上游压缩超时。

[实施计划](../plans/2026-10-20-turn-outcome-feedback.md)保存后连续实施，不再增加计划审批。

## 目标

用户应能在当前阅读位置判断：现在是否仍在执行、刚才这一轮是否正常结束、遇到了什么问题、接下来如何处理。

本次推荐：**运行状态与轮次结果分开表达；每轮只显示一份主要结果，放在该轮消息末尾；执行过程分组只描述自身记录。** 失败原因不能依赖展开过程、回到聊天顶部或悬停才能看到。

## 现场证据与问题

依据用户提供的截图、此前对原生历史和 Web 快照的只读诊断，以及本次对当前源码的复核：

1. 样本最后三轮均因远程上下文压缩超时结束。其中一轮已有大量执行记录和中途说明，后两轮只有用户消息，没有 assistant 回复。原生错误为 `Error running remote compact task: stream disconnected before completion: idle timeout waiting for SSE`。
2. 当前没有活动轮次，Web 显示 `IDLE`。这表示可以接受后续操作，不代表上一轮成功。原生 `systemError` 在无活动任务时被协调为空闲有明确运行时依据，不能为了展示失败而改回“运行中”或错误地锁住输入。
3. `SessionView` 将所有轮次错误集中渲染在聊天记录顶部，再渲染各轮消息。长会话底部因此只看到用户追问，看不到对应的失败原因。
4. `TurnMessages` 将整轮的 `status` 和 `error` 传给每个 `ExecutionGroup`，导致同一轮中的多个过程卡都显示“本轮失败”。这不能说明哪些步骤完成、哪些步骤异常，也不能定位整轮停止的原因。
5. `contextCompaction` 尚未进入共享步骤映射，截图中作为原始类型名单独显示。整轮用时目前附在第一个过程分组上，容易被理解为该分组用时。

上述证据支持“原生轮次已经失败，失败反馈位置和语义有问题”。尚不能区分压缩超时由上游服务、本机网络还是代理链路导致，也不能据此判断整个项目任务已完成。

本 spec 的视觉基线为用户截图，未把新的真实会话接续、发送或手机实机测试作为本轮已完成的验证。实现后的浏览器验收要求见下文。

## 范围与方案选择

采用“轮次末尾结果 + 过程局部状态”，复用现有消息、折叠控件、复制、国际化和发送保护，不引入依赖或全局通知框架。

其他方案不采用：

| 方案 | 问题 |
| --- | --- |
| 仅将错误改成页面顶部横幅或 toast | 长会话底部仍难对应具体追问，短暂提示也不能承担历史结果 |
| 把完整错误塞进每个过程卡 | 重复且需要展开，没有过程记录的失败轮次仍然缺少提示 |

本次承诺修复失败反馈和恢复路径的可理解性，**不承诺通过前端改动消除原生远程压缩超时**。继续原会话仍可能再次触发同一故障。根治压缩问题需要另行定位 CLI、网络或服务端，不能以提示消失作为修复成功。

## 一、每轮结果显示在该轮末尾

`failed` 轮次在最后一条消息或过程分组之后显示一张紧凑结果卡。该卡在所有可折叠过程之外，按 `turn.id` 稳定标识。一轮无论有几个过程分组，都只有一张主要结果卡；只有用户消息，甚至没有可渲染 item 的失败轮次，也必须显示。

示意，数据仅用于说明布局：

```text
用户：请继续处理
▸ 执行过程    18 项记录
Codex：已经完成初步检查，接下来……
▸ 执行过程     6 项记录    含异常记录

! 本轮未完成 · 上下文压缩超时
  本轮未正常结束。已有消息和执行记录已保留。
  可以继续输入。若反复出现，建议在新会话中用简短交接继续。
  本轮用时 12 分钟
  ▸ 查看详情    复制错误

用户：之前的任务完成了吗？
! 本轮未完成 · 上下文压缩超时
  本轮在生成回复前停止，没有收到 Codex 回复。
  可以继续输入。若反复出现，建议在新会话中用简短交接继续。
  ▸ 查看详情    复制错误
```

展示规则：

- 标题直接说明结果和已知原因，不再单独使用信息不足的“本轮失败”。`failed` 的事实、原始错误及原生状态完整保留。
- 无 assistant 消息时，明确“没有收到 Codex 回复”，不显示“执行完成”，也不把已送达的用户消息改成“发送失败”。
- 已有输出时说明“本轮未正常结束。已有消息和执行记录已保留”。中途说明继续保留，不包装为最终答复，不从轮次状态推断整个项目的完成度。
- 没有错误原因时使用“本轮未完成”，正文说明“Codex 未返回具体原因”。不得补写猜测。
- `interrupted` 使用中性的“本轮已中止”，不归为失败。没有明确操作者证据时不写“你已中止”。
- 正常 `completed` 不新增大块成功卡；已有回答承担结果展示。局部工具异常仍可查看，不能据此改写整轮状态。
- `turn.error` 与状态不一致时保留可查的异常详情，按最新原生状态显示，不仅凭错误字段把运行中或已完成轮次改成失败。
- 历史失败卡持久保留，不自动消失。新一轮成功后不删除旧轮次失败记录，也不继续把旧失败当作当前运行状态。

## 二、错误摘要与详情

错误摘要优先使用原生结构化错误码，已有“服务繁忙”映射继续复用。仅在没有专用错误码时，对已确认的明确错误文本进行保守展示分类。

| 已知情况 | 中文摘要 | English |
| --- | --- | --- |
| 远程 compact 错误同时包含 SSE idle timeout | 上下文压缩超时 | Context compaction timed out |
| 原生 `serverOverloaded` | 沿用现有服务繁忙文案 | Reuse the existing overload message |
| 其他明确失败 | 本轮未完成，详情显示原生原因 | Turn incomplete. Show the original error in details |
| 明确中止 | 本轮已中止 | Turn interrupted |

不能将所有 `stream disconnected` 归为压缩超时，不能将超时直接写成“你的网络断开”或“OpenAI 服务故障”。文本分类只影响展示，不参与发送权限、状态协调或重试决策。

“查看详情”使用就地展开，显示可用的原始错误、错误码、轮次开始与结束时间。缺字段不占空位，不展示整份快照。原始错误不翻译、不截断到无法诊断，也不按 HTML 执行。

“复制错误”只复制该轮错误和必要的轮次时间，不默认复制对话、项目路径、私网地址、附件或整份历史。沿用现有复制反馈；失败时不能提示复制成功。

英文核心文案采用简短句子：`Turn incomplete`、`This turn ended before a reply was received.`、`This turn did not finish normally. Existing messages and execution records are preserved.`、`Show details`、`Copy error`。不直接照搬中文长句或堆叠分号。

## 三、执行过程只表达自身记录

保留“执行过程”的入口与记录数，右侧状态从“整轮结果”改为“本组记录情况”：

| 分组情况 | 摘要 |
| --- | --- |
| 当前活动分组 | 展示当前步骤，或确实属于该轮的待审批／待输入状态 |
| 已结束且有明确异常 item | 含异常记录 / Contains issues |
| 已结束但仍有未终结的 item | 有未结束记录 / Contains unfinished items |
| 其他历史分组 | 省略冗余状态 |

同一活动轮次有多个分组时，只有当前分组显示“执行中”，早期分组不跟着整轮一起变为运行或失败。异常与未结束同时存在时优先提示异常，详情保留两类记录。

判定复用现有 `executionRows` 与 `executionIssue` 的一致语义，不新增第二套互相矛盾的规则。尤其保留已有命令退出码 1 的归类规则，不把搜索未命中一律升级为分组或整轮失败。已有异常 item 的定位与展开能力继续保留。

`contextCompaction` 纳入共享步骤映射，中文显示“整理上下文”，英文显示“Compacting context”，进入正常执行记录。历史记录是否失败以该 item 自身证据为准，不能因轮次最终压缩超时，就把此前成功的整理记录全部染红；缺失的压缩 item 不伪造补齐。其他未知类型继续保留可见兜底。

整轮时间明确标为“本轮用时”，仅展示一次，放在轮次末尾的结果或轻量元信息中。运行时可在当前活动分组展示“本轮已用”，结束后归位。没有可靠时间则省略，不用记录数量推算分组或轮次用时。

## 四、顶栏区分空闲与上一轮结果

保留现有运行状态来源和优先级。仅在已同步、可确认无活动任务，且最新轮次为失败时，显示“空闲 · 上轮未完成”。“上轮未完成”是可键盘操作的定位入口，点击滚动并聚焦该轮结果卡，不接续、不重发、不重新执行。

窄屏优先保持现有单行顶栏。可缩短可见文案为“上轮未完成”，但可访问名称必须完整说明“当前空闲，上轮未完成，查看原因”。不新增第二排固定横幅，不挤占输入区或工作区高度。

| 当前情况 | 顶栏规则 |
| --- | --- |
| 最新轮次失败，当前确认空闲 | 空闲 + 上轮未完成定位入口 |
| 新轮次开始或当前等待审批／输入 | 当前运行或等待状态优先，不显示旧失败为当前状态 |
| 新消息正在提交或提交结果未知 | 现有发送／核对反馈优先，不能让旧失败冒充新消息结果 |
| 最新轮次已完成 | 正常状态，不残留上轮未完成入口 |
| 最新轮次已中止 | 空闲 + 中性的上轮已中止摘要 |
| 断线、同步失败、占用或权限待核实 | 沿用现有异常状态优先级，不将历史失败当作当前状态，不凭旧快照宣称当前空闲 |
| 最新轮次未加载或结果不明确 | 不猜测最新结果，沿用已有读取／核对状态 |

迟到的旧轮次事件不能覆盖新活动轮次。展示变化不修改 `Runtime.reconcile`、writer 归属、释放、活动轮次恢复或发送保护。

## 五、恢复路径与既有提示规则保持一致

结果卡提供“查看详情”“复制错误”，恢复继续使用现有输入与新建会话流程，不新增含义不清的“恢复”“接续”“检查结果”按钮。

- 已确认终止的失败，不能靠反复读取同一结果制造“正在恢复”。只读刷新用于同步未知状态，不能被描述为重试执行。
- 原会话可以按现有权限继续输入，但不能承诺下一轮不会再次压缩失败。错误卡给出简短建议：反复出现时，新建同项目会话，携带任务目标、已完成内容、剩余步骤和证据路径。
- 新建会话不等于完整继承原会话。当前不自动生成交接、不复制整份长历史、不把原会话 fork 宣称为清空上下文，也不自动创建或发送新任务。
- 不自动重发最后一条消息，不根据本地计时器合成原生失败，不切换模型或权限，不重启服务，不关闭原会话。审批、未知提交、外部占用和未决写入继续沿用现有保护。
- 与此前提示清理一致：正常同步保持安静，确认的短期成功可收敛；实际失败保留清楚的原因和可用路径，历史结果不冒充当前状态。

## 六、视觉、可访问性与性能

沿用现有暗色主题、间距与控件。失败卡采用低干扰底色、明确图标和文字，避免连续大面积红色，也不能只靠颜色表达失败。默认只展示结果、简短说明、必要建议和轻量操作，长原始错误收进详情。

360／390px 宽度允许文字和操作换行，不截掉原因，不横向溢出。桌面与窄屏共用同一语义，不额外压缩下方工作区。

新失败只通过一个轻量 live region 播报一次。初次载入、加载早期历史和语言切换时，不把全部历史失败作为新 `alert` 连续播报。结果卡本体可定位，详情支持键盘展开，复制反馈不抢焦点。

跟随底部时沿用现有跟随规则显示新结果；用户阅读旧记录时不强制跳底、不抢输入焦点。显式点击顶栏入口才定位结果。插入卡片、展开详情和加载历史要保持阅读位置及草稿。

保留过程稳定标识、手动折叠状态、首次展开惰性挂载、再次展开缓存及输出滚动位置。计算摘要不读取完整工具输出，不因折叠／展开新增历史请求、轮询或原生调用。

## 实施后的验收标准

下列为验收标准，实际通过项和未覆盖范围以[验收记录](../../verification/2026-10-20-turn-outcome-feedback.md)为准。

1. 重现“一轮多过程 + 两轮仅用户消息”的样本。三轮各有且只有一份主要失败结果，分别紧贴各自轮次末尾；所有过程折叠后仍看得到原因。空 items 的失败轮次也不能落入普通空白页。
2. 已完成的过程记录不因整轮失败而重复显示“本轮失败”。异常、未结束、正常记录和退出码 1 的既有语义一致；`contextCompaction` 正确本地化，历史成功整理不被误标失败。
3. 压缩超时、服务繁忙、未知原因、中止、正常完成且局部工具失败、非失败状态附带错误分别验证。没有原生失败证据时不显示确认失败。
4. 顶栏空闲与最新结果分离。覆盖新轮次开始、成功结束、迟到旧事件、待审批／输入、断线、未知提交、外部占用及分页后结果定位。已有发送和状态协调保护不变。
5. 失败保留、中止中性、成功不堆卡。错误原文可展开和复制，复制内容不附带对话和项目隐私。查看、定位、展开和复制不调用会话写入接口。
6. 浏览器实际进入会话页并操作，检查桌面 1280／1440px 与窄屏 360／390px、中英文及现有暗色主题。查看截图，确认原因可见、顶栏单行可用、操作对齐、详情长行换行、输入区及相邻控件没有挤压。
7. 实测 Tab、Enter、Space、焦点可见、顶栏定位与历史重新加载播报。确认草稿、阅读位置、过程展开状态、输出缓存和内部滚动不回退，无重复读取或轮询。
8. 运行针对性展示／状态回归、相关既有会话同步测试、类型与构建检查。记录首轮失败、跳过与未覆盖项。模拟接口验收不等于原生压缩恢复、手机实机或 Safari 验收。

本次已按用户确认实施，实际结果已补充到验证文档。真实故障会话的继续、迁移或再次发送不作为 UI 验收的隐式步骤。
